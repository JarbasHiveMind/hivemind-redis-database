# AGENTS.md — `hivemind-redis-database`

Guidance for AI coding agents (and humans) working in this repository. Read it
fully before making changes. It encodes conventions that are not obvious from the
code and that, if ignored, produce work that will be rejected.

## Repo

A Redis-backed client database plugin for HiveMind-core. It implements the
`hivemind-plugin-manager` `AbstractDB` contract (`RedisDB`, registered under the
`hivemind.database` entry-point group as `hivemind-redis-db-plugin`) and stores
HiveMind client records — API keys, names, and ACL fields such as `is_admin`,
`can_broadcast`, and blacklists — in Redis or Redis Cluster, with optional
RediSearch acceleration. Part of the
[HiveMind](https://github.com/JarbasHiveMind) ecosystem — a protocol for
connecting satellite devices to a hub running
[OpenVoiceOS](https://github.com/OpenVoiceOS). The hub is
[HiveMind-core](https://github.com/JarbasHiveMind/HiveMind-core), which loads
this plugin via `server.json`. The contract this plugin implements lives in
[hivemind-plugin-manager](https://github.com/JarbasHiveMind/hivemind-plugin-manager);
[hivemind-sqlite-database](https://github.com/JarbasHiveMind/hivemind-sqlite-database)
is the sibling backend and the source for the plugin-authoring guide.

## Layout / build / test

- Package module: `hivemind_redis_database/`. Tests live in `tests/` (including
  `tests/e2e/`) — do not create a second test directory.
- Set up a throwaway environment inside your clone; never touch a shared venv:
  `python3 -m venv .venv && VIRTUAL_ENV=$PWD/.venv uv pip install -e ".[test]" --prerelease=allow`
- Run the suite in the foreground: `python -m pytest tests -q`. `tests/e2e/`
  needs `hivescope` and `hivemind_core`; it skips cleanly if either is absent —
  do not work around a real skip.
- `uv`, never `pip`. If latest prereleases fail to install or resolve, that is a
  bug to FIX at the source, not to work around with a pin downgrade.

## Tests

- Adversarial by default. A regression test must **fail before the fix and pass
  after** — prove it by reverting only the source (`git apply -R`, never
  `git stash` across worktrees) and watching the test flip.
- Tests must be mutation-proof: gutting the feature must fail the test. A test
  that only asserts a mock was called, without asserting the real behaviour, is
  weak — note it.
- Never skip a test because an optional dependency is missing.
- CI green is permission to review, not to merge. A non-trivial change gets an
  adversarial review before it lands.
- `tests/test_redisdb.py` mocks Redis with a hand-rolled `FakeRedis` /
  `FakePipeline`; `tests/e2e/` uses the `fakeredis` package's in-process
  `FakeServer`. Neither exercises a real Redis server, RediSearch, or an actual
  Redis Cluster — that only happens in CI's integration jobs (single Redis
  Stack, TLS, Cluster, Stack Cluster). A change to cluster topology detection,
  RediSearch fallback, or the migration tool is not proven safe by the unit
  suite alone; say so in the PR rather than claiming full coverage.

## Repo-specific rules

- API-key resolution (`get_client_by_api_key`) is on the HiveMind-core
  connection-admission hot path. It must fail SAFE: any cache read, decode, or
  write error degrades to the authoritative lookup (`search_by_value` /
  `AbstractRemoteDB`'s scan path), never to a denial and never to admitting a
  client the authoritative record would not have admitted. Do not "optimize"
  this into fail-open behavior on Redis errors.
- The admission cache (`_api_key_record_key`, `ADMISSION_CACHE_TTL`) is a
  derived, expiring cache — never the source of truth. A hit is only accepted
  if the deserialized record's `api_key` still equals the key it was looked up
  under (see `get_client_by_api_key`'s identity check); a mismatch means the
  key was reassigned and the stale record must be dropped, not returned. Any
  new cache added to this backend needs the same identity guard, and must be
  invalidated (`_invalidate_api_key_records`, folded into the same
  pipeline/transaction as the write when possible) on every add, update,
  revoke, and remove — a write that forgets to invalidate reintroduces a stale
  credential for up to `ADMISSION_CACHE_TTL` seconds.
- Redis keys are built exclusively through `_key()` / `_client_key()` /
  `_name_index_key()` / `_api_key_index_key()` / `_scan_pattern()` from
  code-controlled literal parts. Never interpolate an untrusted `api_key` or
  `name` value into a `KEYS`/`SCAN` glob pattern — those values go into exact
  `GET`/`HGET`/`SET` keys, not into pattern arguments, so a key containing
  glob metacharacters (`*`, `?`, `[`) cannot widen a scan.
- Legacy Redis Cluster mode (`_legacy_cluster_mode()`, cluster without
  `cluster_hash_tag`) never populates or reads the admission cache and cannot
  do cross-slot multi-key transactions — its correctness rests entirely on the
  authoritative per-key writes and scan-based search. Do not add a code path
  that assumes a `_pipeline()` call is transactional without checking
  `is_cluster` / `cluster_hash_tag` first.
- Client (de)serialization must round-trip every ACL field — `is_admin`,
  `can_broadcast`, blacklists, and any field added later. A field that
  serializes but does not deserialize (or vice versa) silently downgrades or
  upgrades a client's privileges on the next cache refill or `sync()`; cover
  every ACL field explicitly in any serialization change, not just the ones a
  specific bug touched.
- `sync()` is the repair path for drift (interrupted writes, manual Redis
  edits) — it rebuilds counters, set indexes, and search hashes from the
  authoritative client records, and implicitly relies on the invalidation and
  identity-guard rules above for the admission cache to stay correct after it
  runs.
